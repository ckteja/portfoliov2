Case study · Frame 04.3

A detector that had to live on 4 GB and a fence post.

A 2022 personal project deploying a YOLOv5 wildlife detector to an Nvidia Jetson Nano: collecting the dataset that didn't exist, then making the model small enough to run where the animals actually are.

RoleSolo, end to end
HardwareJetson Nano
Classes15+ custom
Result90% accuracy

The problem

Animal intrusion onto farmland is a detection problem with an awkward constraint attached: the detection has to happen where there is no datacentre, and frequently no reliable network. Streaming video to a server for inference assumes bandwidth that a field boundary does not have, and adds latency to an alert whose entire value is being early.

So the model has to run on the device. That turns a straightforward computer vision task into a systems problem. The Nano offers a modest GPU and a shared memory budget, and every architectural choice is spent against it.

And the data didn't exist

General-purpose detection datasets contain a handful of animal categories, framed as photography: well-lit, centred, taken by someone who intended to photograph the animal. Surveillance footage is none of those things: it is off-angle, motion-blurred, badly lit, and the subject is often partially out of frame. A model trained on the former degrades sharply on the latter.

The dataset had to be collected and labelled from scratch, across 15+ classes, in conditions matching deployment.

The approach

Model choice

YOLOv5 was selected for a specific reason rather than familiarity: it is single-stage. Two-stage detectors propose regions and then classify them, which is accurate but spends inference budget twice. On constrained hardware, a single forward pass producing boxes and classes together is the difference between real-time and a slideshow. YOLOv5 also ships in several width and depth scales, which turns model size into a tunable dial rather than a fixed cost.

Data pipeline

Footage was captured in deployment-like conditions, then labelled across the target classes. Augmentation targeted the failure modes the environment actually produces (varied lighting, partial occlusion, scale variation as animals approach or retreat from the camera) rather than generic transforms.

Deployment

The trained model was then optimised for the Nano and run against a live camera feed on-device, so that a detection produces an alert locally without a round trip.

Results

The deployed system reached 90% accuracy across 15+ classes on the custom dataset, running on-device.

What edge deployment actually costs you

  • Accuracy is traded, not preserved. Shrinking a model to fit a memory budget costs recall on small and distant objects first, which are exactly the early detections an alerting system most wants.
  • Memory is shared. The Nano's CPU and GPU draw on the same pool, so the camera pipeline, preprocessing and the model compete rather than scale independently.
  • Thermal and power limits are real. Sustained inference outdoors is a different workload from a benchmark run, and throttling shows up as dropped frames rather than an error.
  • A custom dataset is a maintenance commitment. Every new species, camera angle or season is a labelling round, and the model quietly degrades until it happens.
  • Threshold choice is a product decision. A false negative is a missed intrusion; a false positive is an alert nobody trusts by week three. Where that line sits isn't a modelling question.
